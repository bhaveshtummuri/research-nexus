# Seed

Deterministic generator and loader for the Research Nexus graph.

Produces **1,415 nodes** and **14,697 relationships** — plus ~2,500
`COLLABORATED_WITH` edges derived at load — from a single seed string. The same
`SEED_RANDOM_SEED` always produces byte-identical output, so demos, screenshots
and integration tests all describe the same graph.

---

## Commands

```bash
npm run db:schema              # apply constraints and indexes
npm run db:seed                # generate and load
npm run db:validate            # run 33 integrity checks
npm run db:stats               # node and relationship counts
npm run db:reset               # delete everything
npm run db:sample              # write a sample slice to seed/sample-dataset.json
```

### Full rebuild in one command

```bash
npm run db:seed -- --reset --with-schema
```

| Flag | Effect |
|---|---|
| `--reset` | Delete every node and relationship first |
| `--with-schema` | Apply constraints and indexes before loading |

`sample` is the only command that does **not** connect to a database —
generation is pure, so a slice can be reviewed without any infrastructure.

## Pipeline

```
SEED_RANDOM_SEED
      ↓
  mulberry32 PRNG          deterministic, reproducible
      ↓
  node generators          10 entity types
      ↓
  relationship generators  power-law citations · community clustering
      ↓
  build.ts                 pure, in-memory, testable without a database
      ↓
  writer.ts                batched UNWIND + MERGE, idempotent
      ↓
  CognoDB
      ↓
  derive.ts                h-index · counters · COLLABORATED_WITH
```

**Generation is separated from writing on purpose.** `build.ts` is a pure
function of the seed string, so the whole pipeline is unit-testable without
infrastructure — the test suite verifies referential integrity, temporal
consistency and distribution shape in ~100 ms. The writer stays a thin batching
layer.

## Why the distributions matter

A uniformly random graph makes every interesting query return noise. Three
properties of real research data are reproduced deliberately.

### Power-law citations

Papers enter a "ticket" pool on publication and gain a ticket each time they are
cited; references draw uniformly from that pool. This is Barabási–Albert
preferential attachment, and it produces the long tail that makes ranking and hub
detection meaningful.

> Seeded result: the most-cited paper has **215** citations; the median has a
> handful.

### Community structure

Co-authors are sampled preferentially from the lead author's institution, their
field, and — with the highest probability — their past collaborators. The result
is genuine research groups, which is why multi-hop collaboration queries return
clusters rather than random people.

### Temporal consistency

- A paper never predates its anchor topic's emergence year
- A paper never cites a dataset released after it
- **A paper cites only strictly earlier work**, which keeps `CITES` acyclic and
  therefore makes lineage traversal terminate
- An author's career start year bounds which papers they can appear on

> Verified: **0** same-or-later-year citations, **0** cycles detected by
> topological sort.

## Idempotency

Every write is `MERGE` on the constrained `id`, so re-running updates the same
nodes rather than duplicating them:

```cypher
UNWIND $rows AS row
MERGE (n:Author { id: row.id })
SET n += row
```

`SET n += row` applies every remaining property in one operation, so adding a
field to a row type never requires touching the writer.

Relationships are written the same way — both endpoints matched by indexed `id`,
then `MERGE` on the relationship — which turns each row into two index seeks
rather than a scan.

## Derived metrics

Computed in Cypher **after** the edges exist, never invented by the generator. A
counter derived from the relationships that actually exist can never disagree
with them.

| Metric | Derivation |
|---|---|
| `Paper.citationCount` / `referenceCount` | `CITES` in/out degree |
| `Author.paperCount` / `citationCount` | `AUTHORED` degree, summed impact |
| `Author.hIndex` | Sort citations descending, take the last position where `citations[i] >= i+1` |
| `University.researcherCount` | `AFFILIATED_WITH` in-degree |
| `Topic` / `Keyword` / venue / dataset `paperCount` | Respective in-degree |
| `COLLABORATED_WITH` | Derived from shared `AUTHORED`, stored once in canonical order |

## Validation

`npm run db:validate` runs **33 checks** from
[`database/validation/`](../database/validation/) and exits non-zero on failure,
so it can gate a deployment.

| Group | Detects |
|---|---|
| Node & relationship presence | An empty label — usually a silently failed step |
| Orphan nodes | Nodes contributing to no traversal (`Keyword` exempt) |
| Required relationships | Paper without author/topic/venue, author without affiliation, project without funder, topic without papers, university without researchers |
| Endpoint labels | The most damaging modelling error — queries return nothing rather than failing |
| Invalid references | Any edge touching a node with no `id` |
| Duplicates | A graph loaded before the constraints were applied |
| Required properties | Stands in for non-portable existence constraints |
| Temporal consistency | Dataset newer than the paper using it; citations to later work |
| Derived-counter accuracy | Drift between a counter and the edges it summarises |
| Undirected canonicalisation | The same fact stored twice, able to disagree |

## Configuration

All in [`src/config/index.ts`](src/config/index.ts).

```ts
export const ENTITY_COUNTS = {
  authors: 300, papers: 600, universities: 50, topics: 100, keywords: 150,
  conferences: 40, journals: 30, datasets: 40, fundingAgencies: 25, projects: 80,
};
```

Scale the dataset from one place — useful for demonstrating traversal performance
on a larger graph.

`RELATIONSHIP_TUNING` controls density: authors per paper, references per paper,
topics and keywords per paper, partnership counts, and the probability weights
that produce the community structure.

| Variable | Default | Effect |
|---|---|---|
| `SEED_RANDOM_SEED` | `research-nexus-2024` | Same value ⇒ identical graph |
| `SEED_BATCH_SIZE` | `500` | Rows per `UNWIND` batch |

## Testing

```bash
npm test --workspace seed        # 26 tests, no database required
```

Property-based rather than value-based: instead of asserting specific names, the
suite asserts *invariants* — every `AUTHORED` edge links a real author to a real
paper, no paper cites itself, the citation distribution is skewed, every
uniqueness constraint the schema declares is satisfiable, and two runs with the
same seed produce identical output.
